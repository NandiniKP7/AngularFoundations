## 1. Custom Component Selector Prefix

Angular-generated components use a selector such as:

```ts
selector: 'app-catalog'
```

The part before the dash is the **selector prefix**:

```text
app-catalog
^^^
prefix
```

Angular uses `app` by default.

For our **Indian Grocery Store**, we changed the prefix to:

```text
store
```

So our selector becomes:

```ts
selector: 'store-catalog'
```

and we use it like:

```html
<store-catalog></store-catalog>
```

### Why use a custom prefix?

A unique prefix helps:

- identify which components belong to our application
- avoid naming conflicts
- keep a large project easier to understand

For our project:

```text
store-catalog
store-product-details
store-header
store-cart
```

It is immediately clear that these belong to the Indian Grocery Store application.

### Configure the Prefix for Future Components

Inside `angular.json`:

```json
{
  "projects": {
    "indian-grocery-store": {
      "prefix": "store"
    }
  }
}
```

Now future components generated by the CLI will automatically use:

```text
store-
```

instead of:

```text
app-
```

Example:

```bash
ng g c product-details --type=component
```

could generate:

```ts
selector: 'store-product-details'
```

### Memory Rule

```text
angular.json prefix
        ↓
future component selectors
```

## 2. Displaying Images from `public/`

Angular uses the `public` folder for static files such as:

- images
- icons
- other files that should be copied directly into the built application

Our file is physically stored here:

```text
public/
└── assets/
    └── BasmatiRice.png
```

But inside an Angular template, we do **not** include `public` in the path.

Correct:

```html
<img src="/assets/BasmatiRice.png" alt="Basmati Rice">
```

Not:

```html
<img src="/public/assets/BasmatiRice.png">
```

and not a local computer path such as:

```text
/Users/.../public/assets/BasmatiRice.png
```

### Why?

Angular serves the contents of `public/` from the application root.

```text
Physical file

public/assets/BasmatiRice.png
             ↓
Browser URL

/assets/BasmatiRice.png
```

That is why your image works with:

```html
<img src="/assets/BasmatiRice.png">
```

### Memory Rule

> `public/` exists in the project, but it disappears from the browser URL.

## 3. Creating Reusable Child Components

Our Catalog component originally contained all the HTML for one product.

We could display several products by copying the HTML repeatedly:

```text
Product HTML
Product HTML
Product HTML
Product HTML
```

But that creates duplication.

If the product layout changes, we would have to update every copied block.

A better design is:

```text
Catalog
   ↓
Reusable ProductDetails component
```

### Create the Child Component

```bash
ng g c product-details --type=component
```

This creates:

```text
product-details/
├── product-details.component.ts
├── product-details.component.html
├── product-details.component.css
└── product-details.component.spec.ts
```

Its selector might be:

```ts
selector: 'store-product-details'
```

### Move Product Responsibility into the Child

The Product Details component should be responsible for displaying **one product**.

So the product HTML moves from:

```text
catalog.component.html
```

to:

```text
product-details.component.html
```

Example:

```html
<div class="product">
  <img src="/assets/BasmatiRice.png" alt="Basmati Rice">

  <div class="details">
    <h2>Basmati Rice</h2>
    <p>Premium long-grain rice.</p>
    <p>Category Type: Rice</p>
  </div>

  <div class="price">
    <p>$12.99</p>
    <button class="cta">Buy</button>
  </div>
</div>
```

Styles that belong to this UI should also move into:

```text
product-details.component.css
```

because Angular component styles are scoped to the component.

## Parent Uses the Reusable Child

The Catalog template can now use:

```html
<ul>
  <li>
    <store-product-details></store-product-details>
  </li>
</ul>
```

The Catalog component must import the child:

```ts
imports: [ProductDetailsComponent]
```

So the structure becomes:

```text
App
 ↓
Catalog
 ↓
ProductDetails
```

or with multiple products:

```text
App
└── Catalog
    ├── ProductDetails
    ├── ProductDetails
    └── ProductDetails
```

## Why Keep `<li>` in the Parent?

The course intentionally keeps:

```html
<li>
```

in the Catalog component instead of putting it inside `ProductDetailsComponent`.

Why?

Because if the child contained:

```html
<li>
```

then it would always need to be used inside a list.

That would reduce reusability.

Better:

```text
Catalog decides layout/container
        ↓
ProductDetails only displays product UI
```

This gives the child component one focused responsibility.

### Memory Rule

> Parent controls where the child is placed.  
> Child controls its own reusable UI.

## 4. Component Lifecycle Hooks

Every Angular component has a **lifecycle**.

That means a component:

```text
is created
   ↓
is initialized
   ↓
may receive/change data
   ↓
may update many times
   ↓
is eventually destroyed
```

Angular gives us special methods called **lifecycle hooks** that let us run code at certain stages.

The most important ones from this lesson are:

```text
ngOnInit()
ngOnChanges()
ngOnDestroy()
```

### `ngOnInit()`

Runs once when the component is initialized.

Common use:

```text
Component starts
      ↓
ngOnInit()
      ↓
load/fetch initial data
```

Example:

```ts
import { Component, OnInit } from '@angular/core';

export class ProductDetailsComponent implements OnInit {

  ngOnInit(): void {
    // initialization logic
  }

}
```

Three steps:

```text
1. Import OnInit
2. implements OnInit
3. Create ngOnInit()
```

Notice:

```text
Interface:
OnInit

Method:
ngOnInit()
```

The method begins with:

```text
ng
```

### `ngOnChanges()`

Runs when Angular-bound input values change.

Think:

```text
Parent sends input
      ↓
input value changes
      ↓
ngOnChanges()
```

This becomes more useful after we learn component inputs.

### `ngOnDestroy()`

Runs shortly before Angular destroys/removes the component.

Common reason:

```text
cleanup
```

For example, cleanup may be needed for resources or subscriptions.

## Other Lifecycle Hooks

Angular has additional lifecycle hooks, including:

```text
ngDoCheck()
ngAfterContentInit()
ngAfterContentChecked()
ngAfterViewInit()
ngAfterViewChecked()
```

You do **not** need to memorize all of them right now.

For this course, focus on:

```text
ngOnInit     → initialize
ngOnChanges  → react to input changes
ngOnDestroy  → cleanup
```

And among those:

> `ngOnInit()` is the one you will see most often at this stage.

## Lifecycle Mental Model

```text
CREATE
  ↓
ngOnInit()
  ↓
component lives / data may change
  ↓
ngOnChanges()
  ↓
...
  ↓
ngOnDestroy()
  ↓
REMOVE
```

## 5. Inline Templates and Styles

So far our component uses separate files:

```text
catalog.component.ts
catalog.component.html
catalog.component.css
```

and connects them using:

```ts
@Component({
  templateUrl: './catalog.component.html',
  styleUrl: './catalog.component.css'
})
```

Angular also allows us to put the HTML and CSS directly inside the component metadata.

## Inline Template

Instead of:

```ts
templateUrl: './catalog.component.html'
```

we can write:

```ts
template: `
  <ul>
    <li>
      <store-product-details></store-product-details>
    </li>
  </ul>
`
```

The backticks:

```text
` ... `
```

allow a multiline string.

## Inline Styles

Instead of:

```ts
styleUrl: './catalog.component.css'
```

we can use:

```ts
styles: `
  ul {
    margin: 0 100px;
    border-top: 2px solid #999;
  }
`
```

So a small component could look like:

```ts
@Component({
  selector: 'store-catalog',

  imports: [ProductDetailsComponent],

  template: `
    <ul>
      <li>
        <store-product-details></store-product-details>
      </li>
    </ul>
  `,

  styles: `
    ul {
      margin: 0 100px;
      border-top: 2px solid #999;
    }
  `
})
export class CatalogComponent {}
```

## Inline vs Separate Files

Both approaches are valid.

| Separate Files | Inline |
|---|---|
| `templateUrl` | `template` |
| `styleUrl` | `styles` |
| Better for larger components | Useful for very small components |
| Cleaner separation | Everything in one file |
| Usually better editor support | Can become crowded |

For a small component, inline HTML/CSS can be convenient.

For a larger component:

```text
TypeScript
+ lots of HTML
+ lots of CSS
```

inside one file can become difficult to read.

That is why the course returns to separate files for the Catalog component.
